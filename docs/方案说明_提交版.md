# 方案说明：Offer 捕手——基于多 Agent 协作的大模型应用算法系统

**项目定位：规则精排 + 语义召回对照 + Eval/Error Analysis，不是普通聊天机器人。**

## 一、问题诊断

学生求职的核心痛点不是"找不到信息"，而是缺乏一个**结构化的决策系统**来回答：哪个岗位最适合我？简历差在哪里？应该先投哪个？这些不是单次问答能解决的，需要多 Agent 协作完成"画像构建→岗位召回→匹配排序→能力诊断→简历改写→投递规划"的完整闭环。

算法层面的挑战：简历和 JD 都是非结构化文本；排序结果必须可解释（面试能讲清为什么）；当前没有真实标注数据，不能靠微调解。

## 二、方案设计

Offer 捕手将求职决策拆解为 7 个 Agent 的协作流程：

Profile Builder（规则+可选 LLM 解析简历）→ JD Intelligence（解析岗位需求）→ Opportunity Scout（关键词+TF-IDF 召回候选池）→ Application Ranker（多维度加权公式排序）→ Gap Diagnosis（能力缺口检测）→ Resume Conversion（规则约束的简历改写）→ Strategy Planner（投递策略+7天计划）。

核心设计：LLM 负责"理解和生成"环节（简历解析、JD 归一化、改写建议），排序和决策交给**可解释公式**：`ApplyPriority = 0.40×Match + 0.30×Pass - 0.15×Risk + 0.15×Growth`。LLM 是可选增强层——无 API Key 时规则版仍可完整运行。

## 三、AI 工具选型

为什么不微调：当前没有真实"简历→JD→初筛结果"标注数据、没有 HR 评价偏好数据、样本量不足（30-80 条岗位）。硬做微调是伪实验。正确路径：当前用 LLM structured output + 可解释公式验证；后续有真实投递反馈后训练 PassScore 预测模型（XGBoost/微调分类器）。

## 四、Eval 与 Error Analysis

**为什么多 Agent 不能只做端到端评测？**端到端"推荐是否满意"无法定位问题在哪个 Agent。本系统拆分为 Match 榜、Priority 榜、Action 三个维度：

当前指标（8 Core + 7 Stress Golden Cases）：
- Core: Match Top1 100%、Priority Top1 85.7%、Action 87.5%、Recall@5 100%、Pass 8/8
- Stress: Pass 7/7、Action 100%

Corpus Eval（7 个代表性 Query，500 条岗位库）：
- Top1 方向命中 >= 71%
- Top5 方向召回 >= 71%
- 空字段数 = 0
- 来源多样性：无单一来源垄断 Top5

Eval 驱动的五轮迭代：初始 Match=42.9% → 修复 E7 误报 → Strategy 阈值校准 Action 25%→87.5% → Matcher 方向 Bonus Match→100% → Stress 全部通过。

剩余 0 个失败 case。系统稳定。

## 五、关键配置

- 岗位库：data/jobs_corpus.json（500 条，HuggingFace 公开数据 + curated seed）
- 岗位库 Schema：统一 title/company/city/direction/stage/skills/jd/source/data_quality_score
- 公开数据源接入：scripts/build_job_corpus.py（支持 HuggingFace Dataset Viewer API）
- Corpus Eval：scripts/eval_corpus_quality.py（7 个代表性 Query 评估大库检索质量）
- 评分权重：src/matcher.py WEIGHTS 可热调整
- 运行：streamlit run app.py（3060 远程）
- Eval：python scripts/run_eval.py

## 七、语义召回对照实验（新增）

**设计原则**：语义召回是**对照实验**，不影响主排序稳定性。规则排序公式仍是主要决策依据。

### 功能说明

Demo 中包含**语义召回证据面板**（岗位详情页第 6 个 Tab），展示：

1. **规则精排 Top5**（ApplyPriority 排序结果）
2. **语义召回 Top5**（Embedding + FAISS 向量检索结果）
3. **两个榜单的交集**（Top5 中同时出现在两个榜单的岗位）
4. **为什么语义召回命中这个岗位**（匹配原因说明，来自 `matched_reason`）
5. **当前使用模型、设备（CUDA/CPU）、语料库规模**（当前 500 条）

### 技术实现

- 使用 `sentence-transformers/all-MiniLM-L6-v2` 编码岗位文本和简历文本
- 使用 `FAISS IndexFlatIP` 建立向量索引（内积 = cosine similarity，当向量归一化后）
- 自动检测 GPU（CUDA）并优先使用，`pytorch123` 环境（PyTorch 2.3.1 + CUDA 11.8）
- 模型只读加载，不修改模型文件，不微调、不训练

### 与规则排序的分工

| 方法 | 作用 | 是否影响主排序 |
|------|------|------|
| 规则精排（ApplyPriority 公式） | 主要决策依据，可解释 | 是 |
| 语义召回（Embedding + FAISS） | 对照实验，发现规则可能遗漏的岗位 | 否（仅展示） |
