# AI 工具选型与数据策略

> 本文档说明 Offer 捕手各模块的 AI 使用策略、数据来源，以及"为什么当前不做微调"的决策依据。
>
> **本文档的核心作用**：增强项目的**算法可信度**——说明为什么当前用 LLM API + 多 Agent 编排 + 可解释排序，而不是盲目微调。

---

## 一、当前模型使用策略

Offer 捕手采用**分层 AI 策略**，而不是"全交给大模型"：

| 层级 | 技术选型 | 职责 | 算法原因 |
|---|---|---|---|
| 理解/生成层 | LLM API（可选） | 简历解析、JD 理解、诊断解释、简历改写、策略总结 | LLM 擅长语义理解，适合非结构化文本 → 结构化画像 |
| 决策/排序层 | 规则公式 + 可解释权重 | MatchScore、PassScore、RiskScore、ApplyPriority | **可解释性约束**：面试官可追问权重来源，黑盒 LLM 打分无法满足 |
| 召回层 | 关键词 + TF-IDF 模拟 | Opportunity Scout 岗位候选池 | 稳定、可解释，语义匹配不是唯一核心 |
| 数据层 | 小型岗位库（Demo） | 快速验证多 Agent 协作流程 | 数据稀缺时先搭建算法框架，再逐步扩大数据 |

**核心原则：** LLM 负责"理解和生成"，排序决策必须"可解释、可复现"，不能黑盒。

---

## 二、各 Agent AI 使用策略

| Agent | 当前实现 | 是否调用 LLM | 算法原因 |
|---|---|---|---|
| Profile Builder Agent | 规则抽取 + 可选 LLM 结构化解析 | 可选 | 简历字段复杂、格式不统一，LLM 适合做结构化理解 |
| JD Intelligence Agent | 岗位库结构化字段 + 可选 LLM 抽取 | 可选 | JD 表达不统一（"精通"vs"熟悉"），LLM 适合归一化 |
| Opportunity Scout Agent | 关键词 / 轻量相似度召回 | 暂不依赖 | 召回阶段要求稳定、可解释，语义匹配不是唯一核心 |
| Application Ranker Agent | 公式计算 Match/Pass/Risk/Priority | 不直接交给 LLM | **排序决策必须可解释**，公式权重可在面试中讲清楚 |
| Gap Diagnosis Agent | 规则检测 + 可选 LLM 解释 | 可选 | 规则能稳定发现缺口，LLM 适合生成可读诊断文本 |
| Resume Conversion Agent | 模板改写 + 可选 LLM 优化 | 可选 | LLM 擅长语言优化，但改写逻辑需要有规则约束 |
| Strategy Planner Agent | 规则策略 + 可选 LLM 总结 | 可选 | 投递策略逻辑固定，LLM 只做自然语言总结 |

**LLM 调用开关：** `app.py` 侧边栏提供 `启用 LLM 精排（需 .env 配置）` 开关，无 API Key 时所有 Agent 自动回退到规则版，Demo 仍可完整运行。

## 三、为什么不做微调（算法诚信）

当前阶段**不做微调**，不是因为不会，而是因为：

### 1. 没有真实标注数据

微调需要"简历 → JD → 初筛结果（通过/不通过）"的大规模标注数据，当前项目没有真实 HR 初筛反馈数据。

### 2. 没有 HR 评价偏好数据

PassScore 的核心是"这位 HR 会筛掉哪些简历"，这需要企业级标注偏好数据，学生项目不可能获得。

### 3. 没有足够多的岗位/学生样本

微调需要覆盖不同方向（大模型/Agent/RAG/推荐/后端）的大量样本，当前 30-80 条岗位数据远不够做可靠微调。

### 4. 硬做微调容易变成"伪实验"

在数据不足时强行微调，结果不可复现、不可解释，反而降低项目可信度。

### ✅ 推荐表达（面试/比赛这么说）

> 当前阶段不进行微调，而采用 **LLM structured output + 可解释排序公式 + 小型岗位库验证流程**。
> 后续若接入真实投递反馈（学生是否收到面试通知），可训练 **PassScore 预测模型**（XGBoost/LightGBM 或微调分类器）；
> 若获得 HR 简历评价偏好数据，可做**简历改写偏好优化（RLHF 方向）**。
>
> 用户已有 `llm_for_rec_agent` 项目已经证明过 SFT/DPO 能力，Offer 捕手不需要重复证明这一点。

## 四、数据从哪里来

### 当前 Demo 数据（已内置）

| 数据类型 | 内容 | 用途 |
|---|---|---|
| 岗位 JD | 30-80 条，覆盖大模型应用算法、Agent、RAG、LLM4Rec、推荐算法、AI 后端、数据分析 | 多 Agent 协作流程验证 |

| 技能关键词词典 | 按方向分类（LLM/Agent/RAG/推荐/后端） | 规则版解析 + 关键词覆盖率计算 |

## 五、模型选型建议

| 方案 | 优点 | 缺点 | 当前是否采用 |
|---|---|---|---|
| **纯规则** | 稳定、可解释、零成本 | 语言理解能力弱，泛化性差 | 用作 fallback（无 API Key 时） |
| **LLM API** | 快速上线、效果好、易部署、支持结构化输出 | 成本依赖 API、稳定性依赖外部服务 | ✅ **当前推荐** |
| **本地部署模型** | 数据可控、可离线运行、可微调 | 3060 显存有限（按实际机器而定），部署维护成本高 | 暂不主线 |
| **微调模型** | 可学习业务偏好、效果稳定后可降本 | 缺真实标注数据，短期不可靠，容易过拟合 | 未来演进方向 |
| **Embedding 向量召回** | 适合语义匹配、可扩展到大库 | 不是本项目主角（已有项目 `llm_for_rec_agent` 已覆盖 RAG） | 后续增强 Opportunity Scout |

**LLM API 选型建议（按优先级）：**

1. **DeepSeek V3/Chat** — 中文理解强、JSON 输出稳定、价格低 ← 当前推荐
2. **Qwen3/Qwen2.5** — 阿里开源，支持 function calling，可本地部署
3. **GPT-4o/GPT-4.1** — 效果最好，但成本高，适合最终版精排

## 六、最终技术定位

**Offer 捕手当前合理定位：**

> **LLM API + 多 Agent 编排 + 可解释排序决策 + 小型岗位库验证 + 未来真实投递反馈训练 PassScore 模型。**

**一句话区分与已有项目：**

- `llm_for_rec_agent` 证明你会做 **RAG/Agent 技术系统**（召回、排序、SFT/DPO、幻觉评估）
- `Offer 捕手` 证明你能把 **Agent 技术做成可解释的决策算法系统**（多 Agent 协作、可解释排序、简历转化率优化、投递策略规划）

**演进路径：**

```
当前（Demo 验证）
  → 接入校招官网 JD（扩大岗位库）
  → 接入学生投递反馈（优化 ApplyPriority 权重）
  → 训练 PassScore 预测模型（XGBoost/LightGBM 或微调分类器）
  → 简历改写偏好优化（获得 HR 反馈后做 RLHF 方向）
```

## 七、商业闭环（落地价值，非主线）

> 商业闭环是项目的**落地价值补充**，不是主线。主叙事仍然是"基于多 Agent 协作的大模型应用算法系统"。

若有真实投递反馈，系统可形成完整数据驱动闭环：
1. 学生投递 → 收到面试通知/拒信
2. 反馈给 PassScore 模型 → 优化初筛通过率预测
3. 反馈给 ApplyPriority 公式 → 优化投递优先级
4. 反馈给 Resume Conversion Agent → 优化改写策略

这部分作为"算法落地价值"的补充，不盖过"大模型应用算法 / Agent 应用算法"的主线。
