# 方案说明：Offer 捕手——基于多 Agent 协作的大模型应用算法系统

## 一、问题定义（算法视角）

> 如何用一个**多 Agent 协作系统**解决"学生→岗位"的匹配与决策优化问题？

核心问题：非结构化文本理解、多维度可解释排序、数据稀缺下的算法验证。

## 二、算法方案

7 个 Agent 协作：Profile Builder → JD Intelligence → Opportunity Scout → Application Ranker → Gap Diagnosis → Resume Conversion → Strategy Planner。排序公式可解释：`ApplyPriority = 0.40×Match + 0.30×Pass - 0.15×Risk + 0.15×Growth`。LLM 是可选增强层，无 API Key 时规则版仍可完整运行。

## 三、AI 工具选型

LLM 负责"理解和生成"，排序决策交给"可解释公式"。不做微调原因：无真实标注数据、无 HR 偏好数据、样本量不足——硬做微调是伪实验。正确路径：当前 LLM structured output + 可解释公式验证；后续有真实反馈后训练 PassScore 预测模型。

## 四、Eval 与 Error Analysis 设计

**为什么多 Agent 不能只做端到端评测？** 端到端"推荐是否满意"无法定位问题在哪个 Agent。本系统拆分为三个维度：

| 维度 | 指标 | 当前值 |
|------|------|--------|
| Match 榜 | Top1 准确率 | **100%** |
| Priority 榜 | Top1 准确率 | **85.7%** |
| Action | 投递动作准确率 | **75.0%** |
| Recall@5 | Match + Priority 召回 | **100%** |

**Eval 驱动的四轮迭代：**
1. 初始：MATCH=42.9%，E7 误报 ×8（gaps 类型处理错误）
2. 修复 E7：消除全部 8 个误报
3. Strategy 校准：ACTION 25%→75%，MATCH 升至 71.4%
4. Matcher 方向+标题 Bonus：MATCH 升到 100%

**剩余问题（3/8 case）：** case_03 NLP→LLM 的 Priority 榜排序仍可优化（非召回崩溃）；case_05/07 的 Action 分歧是合理外部上下文差异（城市/毕业状态），不是系统 bug。

**下一步：** 扩充岗位库覆盖更多方向（纯推荐、纯 CV），增加 golden cases 到 15-20 个；接入 real 投递反馈后训练 PassScore 预测模型。

## 五、关键配置与运行

- 岗位库：`data/jobs.json` | 权重：`src/matcher.py` WEIGHTS
- Eval：`python scripts/run_eval.py`
- 运行：`streamlit run app.py`（3060 远程）
